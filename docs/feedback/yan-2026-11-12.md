# Feedback from the yan project, 2026-11-12

Report, not normative. Proposals here need an ADR or a spec PR before they apply.

## Context

Yan (zaofang/yan) is a language toolchain run by one part-time lead with Claude agents since 2026-10-30: issue and PR numbers passed 1,050 in two weeks, a coordinator session that dispatches one task thread at a time, and since 2026-11-11 an unattended "autodevelop" loop that pulls from a queue issue and merges on green. Yan did not adopt Mandate (lead's decision, 2026-11-12), so this is evidence from a parallel process that faced the same problems. It complements `docs/feedback/ceteris-2026-11-12.md` (PR #21); where a point is already there, this report adds Yan's evidence and cites it as "ceteris P<n>" instead of repeating it.

Evidence is cited as `yan#N` (issues and PRs in zaofang/yan).

## What worked

1. **Issues as the queue.** One master tracker (yan#449) with issue rules, per-initiative trackers (yan#1024 retrospective queue, yan#782 efficiency), and every thread linking, updating and closing its issue. A merge-log comment on yan#449 is written by CI. Supports Mandate's "GitHub is the work queue". The failure was keeping a second copy of the queue in agent memory (finding 9).
2. **Mechanical domain gates as required checks.** `tools/guard.py` (agents never edit `tests/` or `conformance/`, keyed on PR author, not branch name), `tools/rows.py check` (spec rows and codes unique, cited, rendered), a blocking interpreter/native differential run (234 programs, 0 unexplained divergences), a retired-name lint and a 3,000-line ratchet. None of these depended on an agent reading its instructions. Supports ADR-0013.
3. **A law table with an enforcement column.** `docs/development-laws.md` lists 16 laws, each with its enforcement mechanism and a status: None, Partial, Gated, Enforced. It made the gap between rule and gate visible and drove the retrospective queue: five laws moved to Gated in two days (yan#1028, yan#982). See proposal P6.
4. **Numbers last.** Row numbers and diagnostic codes are assigned by a tool in the final commit after merging main; drafts carry D1, D2 labels. Before this (2026-11-01), parallel threads collided on numbers repeatedly. Mandate's `mandate adr new` assigns the number when the branch is created, which reintroduces the collision. See P5.
5. **Cards with a default.** Decisions go to the lead as multiple-choice cards with one recommended option (ceteris P8). Since 2026-11-12 (yan#1030), a reversible low-stakes card closes on the recommendation after 24 hours without an answer; goal-changing or irreversible cards wait. Before the default, 34 issues were labeled for the lead and work stalled behind them. See P4.
6. **Park and continue.** When a task in the loop stalls (CI leak, decision, lead-owned path), the loop parks it with a note on its issue, adds it to a "needs lead" list and takes the next task. Between 02:23Z and 14:06Z on 2026-11-12 the loop merged six PRs (yan#1038, yan#1045, yan#1047, yan#1050, yan#1051, yan#1052) while two waited on the lead (yan#1040, yan#1046). Matches `agents.md` Blocked; P3 adds what parking also requires.
7. **Generated, dated figures.** Reports carry a commit and date on every figure, are generated by `tools/report.py` (yan#1029) and fail lint when older than 7 days. The weekly report workflow opens its own PR. See P7 for the digest.
8. **Stage claims.** Every PR states its stage: working (runs on both backends), right (conformance case and clean differential), fast (instruction counts against a baseline). Review asks one question: is the claimed stage proven?

## What did not work

Each finding: observation, why it matters, proposed change.

### 1. The loop went idle after a report

**Observed.** The autodevelop loop posted its five-task report at 05:49Z on 2026-11-12, ended its turn, and did nothing until the lead asked for an update at 12:52Z: seven hours idle with workable issues open. The same happened earlier in the night (03:41Z to 04:59Z). Each report or status post was treated as an end point.

**Why it matters.** ADR-0005 promises agents that "pull work continuously", but the contract has no liveness rule, and running agents is a Mandate non-goal. Nothing in the spec notices a stalled project; the digest is weekly.

**Proposal (P1).** In `agents.md` Work: "Reporting is not a stopping point. While `mandate next` returns an issue, the session takes it." In `workflow.md` Reporting and `mandate status`: a project in state active whose last agent activity (claim comment, push, PR event) is older than a threshold (default 2 hours) is reported `stalled`, first in the digest, next to gates and blocks.

### 2. Lead-owned paths became the bottleneck

**Observed.** In one night, every PR touching `.github/` waited for the lead: the CI ruleset (yan#1037), blocking differential step (yan#1040), DCO exemption for Dependabot (yan#1039), the weekly report workflow (yan#1046) and five Dependabot Action bumps (yan#1032 to yan#1036). Parked PRs went stale: the lead found conflicts on yan#1040 and yan#1034 and had to ask for rebases.

**Why it matters.** Mandate gates all of `.github/` and gives the App no workflows permission, so every CI improvement will queue for the BDFL. That is correct for safety; the cost is waiting time and rot, which the spec does not address.

**Proposal (P2).** In `workflow.md`: (a) the agent that opened a gated PR keeps it mergeable: after each merge to main it re-checks parked PRs and merges main into them; (b) the digest lists open gates with age and mergeable state; (c) one gated PR may batch several workflow changes for the same milestone, so the BDFL reviews once. Keep the gate itself.

### 3. A required check that never reports

**Observed.** The first `main` ruleset required a status context named `rows`, but the job that runs `tools/rows.py check` is named `check`. Every PR waited on a check that would never arrive. Separately, path-filtered jobs (`rust`, `formal` skip on docs-only PRs) only pass because skipped jobs count as success, which is easy to break by reworking the filter.

**Why it matters.** Mandate requires `mandate-check`, `mandate-gate` and "project CI" as checks, defined in ruleset JSON. Milestone 002 already lists the risk that `mandate-gate` may not re-run on review events. A mismatched context name blocks every merge and looks like an agent failure.

**Proposal (P3).** In `enforcement.md` `mandate-check`: every required context in the committed ruleset JSON is the name of a job that runs, without path filter, on every `pull_request`; project CI exposes one aggregate job (e.g. `ci`) as its required context. `mandate sync` refuses to apply a ruleset that fails this.

### 4. Agent-side permission refusals look like gates

**Observed.** The Claude Code permission classifier refused `gh pr merge` in sessions on the lead's Mac (yan#788) while a merge through the GitHub MCP tool succeeded; it refused an amend and force-push to fix a missing DCO sign-off; it refused a downloaded scanner binary; it refused repository creation even after the lead's yes. Each refusal cost a round trip to the lead.

**Why it matters.** `agents.md` says "`gh pr merge --auto --squash`" and the CLI is bash over `gh`. The runner's own permission layer is a second, unplanned gate whose rules differ per machine and change without notice. Agents cannot tell a policy refusal from a broken tool.

**Proposal (P4).** In `agents.md`: merge and auto-merge may use any GitHub API path (CLI, REST, MCP); the command is not part of the contract. In the template: a gated `.claude/settings.json` with the allow rules Mandate's commands need, so the classifier and the gates agree. A refusal by the runner is reported as `needs-env` (ceteris P9), not retried.

### 5. Agent identity: the contract cannot be met on the main runner

**Observed.** claude.ai cloud sessions act on GitHub through the user's own connection. Commits and PRs from agents appear as the lead: on the first project the lead could not approve an agent PR as code owner because GitHub saw it as his own. Yan never created an App. Its guard keys on PR author, Bot type or agent branch prefix; since agent PRs are authored by the lead's account, only the `claude/` prefix identifies them, and a canary job exists just to prove a non-`claude/` agent branch is still caught.

**Why it matters.** ADR-0012 and `agents.md` Never ("Act as the BDFL's account") cannot be met by today's claude.ai runner. Worse, the ruleset's admin bypass means an agent holding the BDFL's token inherits the bypass, so every path gate collapses for exactly the sessions Mandate expects to run. Issue #3 (create the App) is a `bdfl` task, but no spec text says what holds until the App exists or for runners that cannot use it.

**Proposal (P5).** Amend ADR-0012 by a new ADR: (a) a runner that cannot authenticate as the App is a degraded runner; `mandate status` reports which identity a project's recent agent commits used; (b) under a degraded runner, gated paths are enforced by a required check (Yan's guard pattern) that fails any PR touching a gated path unless it carries the BDFL's review or is merged by the BDFL, since code-owner review cannot distinguish agent from BDFL; (c) remove the admin bypass from the ruleset and let the BDFL's own PRs pass by that same check instead.

### 6. Branch names are fixed by the runner

**Observed.** claude.ai sessions get an assigned branch (`claude/project-thread-<id>`) and may not push elsewhere without explicit permission. This PR is on such a branch, as are #2, #19, #20 and #21 in this repository. Issue #18 already records this.

**Proposal (P6).** In `workflow.md` Branches: the issue link lives in the PR body (`Closes #N`), checked by `mandate-check`; branch names are free. Drop `agent/<issue>-<slug>`.

### 7. Merge method

**Observed.** Yan merges with merge commits by rule. The reason was DCO: a sign-off check runs on every non-merge commit, and per-commit sign-offs and stage commits stay visible. When a missing sign-off needed a history rewrite, the runner refused the force-push (finding 4).

**Why it matters.** Mandate is squash-only. That is compatible with DCO only if the squash commit carries the sign-off, which GitHub writes from the merger's account, not the author's.

**Proposal (P7).** Keep squash as the default, but state in `workflow.md` how sign-off survives a squash (the PR body's `Signed-off-by` lines go into the squash message) and make the merge method a project setting recorded in `AGENTS.md`, checked against the ruleset by `mandate-check`.

### 8. Gating the spec gated the wrong thing

**Observed.** Yan's spec PRs first needed the lead's merge; once the lead was answering a card for every decision, the merge click became a second, empty approval and was replaced by standing approval to merge after the card (ceteris P6 saw the same). Separately, gating did not stop spec growth: at the 2026-11-12 retrospective 650 of 879 spec rows had no conformance case, and the lead froze new rows until that falls to 60%.

**Why it matters.** The tooling profile gates `docs/spec/`. What the BDFL needs to control is which decisions enter the spec and how far the spec runs ahead of the implementation; the merge click controls neither.

**Proposal (P8).** Combine ceteris P1 with a decision reference: a spec PR whose every change cites an accepted decision (ADR, or an answered `gate` issue) merges ungated on green; anything else is gated. Add a profile metric "spec debt" (normative statements with no test) to `mandate digest`, and a rule that it may not grow across two consecutive digests without a BDFL decision.

### 9. State in chat and memory drifted

**Observed.** Yan's decisions were answered on chat cards and recorded in agent memory; roadmap, work table and about 220 research studies live in claude.ai documents outside the repository (yan#1031 exports them). Memory lagged reality within hours: it still listed yan#1037 as pending after it merged, and a note that hosted runners never start remained after the repository went public and they did.

**Why it matters.** Mandate's success criterion "the BDFL never reconstructs project state from chat history" is the right goal; Yan shows the failure mode is not chat but any store besides the repository and issues. Ceteris P11 proposes capping memory.

**Proposal (P9).** In `agents.md`: a decision made outside GitHub (a card, a chat answer) is recorded on its issue in the same session, quoting the BDFL's words and time, before work on it starts. Session memory may hold pointers and standing preferences only, never queue order or open items. `mandate-check` fails on links from `docs/` to private documents (ceteris P7).

### 10. Work outside the milestone

**Observed.** Yan's most valuable week of process work (honest CI, generated reports, retired-name lint, native parity) came from a retrospective queue (yan#1024) that cut across milestones M1 to M4. Under `agents.md` ("stay inside the issue and the milestone") it would have waited for a close-out.

**Proposal (P10).** In `workflow.md`: the BDFL may add any `triage` issue to the active milestone by setting its milestone; that act is the scope approval. Agents never do it themselves. A retrospective is a normal source of such issues.

### 11. CI that does not run

**Observed.** From 2026-10-30 until the repository went public on 2026-11-12, hosted runners did not start on the account (no Actions minutes); jobs failed with zero steps, and on the first project the lead said "disregard CI and merge regardless". Every gate that lives in CI was off.

**Proposal (P11).** In `artifacts.md` bootstrap and `mandate status`: a project cannot leave inception until a canary workflow has run on a PR; the digest reports any project whose last required-check run is older than its last push as `ci-down`, ahead of everything else.

### 12. Failure classification and retry budget

**Observed.** Yan retries a red CI once only when it shows an infrastructure signature (HTTP 5xx fetching a toolchain), never for a code failure, and allows two fix attempts per PR. This removed most wasted reruns.

**Proposal (P12).** In `agents.md` Blocked: replace "three failed attempts" with "two fix attempts; an infrastructure failure gets one rerun that does not count". Name the signature list in `AGENTS.md`.

### 13. Reporting by count, not time

**Observed.** The loop reported every five completed tasks. Task length varied from twenty minutes to several hours, so the lead asked for updates twice in one night.

**Proposal (P13).** Covered by P1's `stalled` state for the push channel; the digest stays weekly. Count-based reports are a runner choice, not spec.

### 14. Model and cost routing

**Observed.** Yan's project instructions route models by task class (cheap model for search, lint and numbering; mid model by default; strongest model for design and second-attempt debugging), cap each thread at 25 turns, and write the model into each issue (`Model: Haiku`). Ceteris P12 covers cost logging.

**Proposal (P14).** Optional `## Model` line in the task issue template, read by runners; Mandate does not prescribe models.

## Conflicts found when evaluating Mandate for Yan

Recorded on 2026-11-12 when the lead declined adoption. Each is addressed above.

| Mandate rule | Yan practice | Finding |
|---|---|---|
| Squash merge only | Merge commits, DCO per commit | 7 |
| `docs/spec/` gated by CODEOWNERS | Standing approval to merge spec PRs after a card | 8 |
| Agents act as a GitHub App | Agents act through the lead's connection | 5 |
| Branches `agent/<issue>-<slug>` | Runner-assigned `claude/...` | 6 |
| Stay inside the milestone | Retrospective queue across milestones | 10 |

## Priorities

If only three change: P5 (identity, because the gates do not hold without it), P1 (liveness, because unattended work is the point), P3 (required checks that can actually report).
